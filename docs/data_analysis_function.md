二、总体设计思路

本次调整的核心不是单纯改几个页面名称，而是要把系统从“能问数、能出图”的工具，升级成一个 具备数据语义、分析意图、分析经验、多 Agent 推理、结果复用能力的智能数据分析能力。

新版系统应形成五层闭环：

系统配置
→ 数据资产
→ 知识记忆
→ 智能分析
→ 经营周报复用

其中：

* 系统配置 解决“系统怎么连外部数据和模型”；
* 数据资产 解决“系统知道有哪些表、字段、指标、主题”；
* 知识记忆 解决“系统知道业务问题通常怎么分析”；
* 智能分析 解决“大模型如何拆问题、写 SQL、写 Python、生成结论”；
* 经营周报 解决“分析结果如何应用的问题”。

这里有一个关键原则：

数据接入、模型调用、SQL 执行、Python 渲染、结论总结都属于后台能力；页面只负责配置、触发、编辑、展示和复用。

三、菜单结构调整方案

1. 系统配置菜单调整

系统配置菜单下保留并优化三个核心子模块：

系统配置
├── 模型接入
├── 数据接入

调整要求：

1. 模型接入 和 数据接入 两个子模块移动到 系统数据参数 上方；
2. 数据接入页面目前不做大改；
3. 数据接入页面只维护接入 QBI 或其他数据平台所需的连接信息；
4. 真正的数据同步、接口调用、SQL 执行在后端服务完成。

数据接入的边界要清楚：

页面维护连接配置，后端负责真正的数据接入、SQL 执行、字段同步、结果返回。

2. 原始表 Tab

原始表用于管理从 QBI 或底层数据平台同步进来的底层底表。

原始表的定位

原始表不是给用户直接分析用的快捷入口，而是系统理解数据的基础资产。

它解决的问题是：

这张表是什么？
来自哪里？
主键是什么？
有哪些字段？
字段是什么意思？
字段有哪些枚举值？
字段应该怎么使用？
哪些字段不能直接使用？
哪些字段需要结合业务口径解释？

原始表建议字段

字段	说明
表英文名	QBI 中的底表名称
表中文名	业务可读名称
表来源	QBI / 数仓 / 其他系统
表类型	明细表 / 维表 / 事实表 / 汇总表
主键	表主键或联合主键
时间字段	常用日期字段
机构字段	机构、支行、客户经理等组织字段
客户字段	客户号、客户ID、商户ID等
表说明	表的业务含义
更新频率	日更 / 周更 / 月更 / 实时
使用限制	例如不能直接汇总、需要去重、只保留最近状态
示例 SQL	常见查询示例

字段级语义层

原始表下还需要管理字段级信息。

建议字段如下：

字段	说明
字段英文名	底表字段名
字段中文名	业务名称
字段类型	string / number / date / enum
字段解释	这个字段代表什么
枚举值	如客户类型、状态、产品类型
是否主键	是否属于主键
是否时间字段	是否常用于时间过滤
是否指标字段	是否可用于计算指标
指标口径	如果是指标字段，需要说明统计口径
关联指标	关联指标字典中的指标
业务注意事项	如是否含撤销、是否含测试数据
示例用法	SQL 示例或业务解释

这部分字段逻辑通过接口从 QBI 获取基础信息，再由系统补充字段级语义描述。

也就是说：

QBI 提供技术元数据；
本系统补充业务语义层。

3. 主题表 Tab

主题表用于管理系统中被沉淀和复用的分析主题。

主题表的定位

主题表不是底层底表，而是分析场景下可复用的主题数据逻辑，通常是汇总表、宽表、指标聚合 SQL 或某类固定分析逻辑。

它解决的问题是：

这个经营分析主题要看哪些数据？
对应的 SQL 是什么？
适合什么分析场景？
能不能作为智能分析页面的快捷入口？
能不能被经营周报引用？

主题表建议字段

字段	说明
主题名称	如“机构经营概览”“财富中收分析”“客户经理贡献分析”
主题编码	系统唯一编码
主题描述	说明这个主题解决什么问题
主题 SQL	可直接提交给 QBI 执行的 SQL
主题字段	SQL 返回字段
字段解释	每个返回字段的业务含义
适用场景	周报、双周报、经营分析、客户经理督导等
关联意图	对应知识记忆中的分析场景 / 分析目的
关联经验	对应分析经验名称
是否快捷展示	是否在智能分析输入框下方展示为快捷主题
是否可被周报引用	是否可进入经营周报模块库
创建来源	人工创建 / 智能分析保存 / 系统预置
更新时间	最近更新时间

主题表有两个来源：

1. 系统角色人工维护；
2. 智能分析结果保存后沉淀。

主题表的 SQL 一旦被保存，就可以在智能分析页以快捷主题形式展示。用户点击后，系统自动将主题提交给后台智能分析引擎。

2. 意图管理

意图管理用于管理系统可识别的数据分析意图。

意图分为两层：

└── 分析目的

例如：

分析场景：机构经营分析
分析目的：
- 看整体经营表现
- 找异常指标
- 找落后机构
- 找客户经理问题
- 找产品结构问题
- 找增长机会

再如：

分析场景：客户经理督导
分析目的：
- 看客户经理目标达成
- 找贡献不足原因
- 找存量客户流失
- 找高潜客户转化机会

意图管理建议字段

字段	说明
分析场景	一级意图
分析目的	二级意图
意图描述	说明这个意图解决什么问题
关键词	用于意图识别
关联主题	关联主题表中的主题名称
关联指标	关联指标字典
关联经验	关联分析经验
适用页面	智能分析 / 周报 / 双周报
是否启用	控制是否参与意图识别
示例问题	用户可能输入的问题样例

意图管理与主题表、分析经验之间应形成映射：

意图管理
→ 主题表
→ 分析经验
→ 指标字典
→ 原始表字段语义

这样大模型在识别用户问题时，不是凭空分析，而是先在系统已有的意图、主题、指标和经验中找依据。

3. 分析经验

在知识记忆下新增或强化 分析经验 模块。

分析经验的定位

分析经验用于记录当前机构、当前业务中已经沉淀出来的常规分析方法。

它解决的是：

这个主题通常怎么分析？
先看什么？
再看什么？
哪些指标是核心？
哪些变化代表异常？
常见结论有哪些？
风险判断规则是什么？

分析经验建议字段

字段	说明
经验名称	建议与主题表名称一致
关联主题	对应主题表
关联意图	对应分析场景和分析目的
分析步骤	固定分析路径
核心指标	本经验依赖的指标
判断规则	例如同比下降、环比下滑、目标达成低于80%
常见结论	用于小模型总结时参考
风险提示	例如数据延迟、指标口径变化
示例总结	标准结论模板
适用机构	当前机构 / 全部机构
是否启用	是否参与检索

与主题表的关系

建议保持一个明确规则：

主题表负责“取什么数据”，分析经验负责“拿到数据后怎么分析”。

二者可以名称一致，也可以通过关联字段建立映射。

例如：

主题表：财富中收分析
分析经验：财富中收分析

主题表中保存 SQL 和字段逻辑，分析经验中保存分析路径、判断规则和常见结论。

4. 知识记忆 Tab 无法点击的修复建议

你提到当前知识记忆下的 Tab 模块无法点击使用。这个问题通常不是业务逻辑问题，而是前端路由、Tab Key 或组件状态绑定的问题。

建议从以下几个方向检查：

可能原因一：Tab Key 与路由不一致

例如页面配置中是：

knowledge-file
memory-experience

但组件中使用的是：

knowledgeFile
memoryExperience

会导致点击后状态更新了，但内容区不渲染。

修复原则：

菜单路由、Tab Key、组件枚举值三者统一。

⸻

可能原因二：Tab 内容组件未注册

Tab 标题渲染出来了，但对应的内容组件没有挂载。

应检查：

tabs = [
  { key: 'intent', label: '意图管理', component: IntentManage },
  { key: 'file', label: '知识文件', component: KnowledgeFile },
  { key: 'experience', label: '分析经验', component: AnalysisExperience }
]

每个 Tab 都必须有明确 component。

⸻

可能原因三：默认 activeKey 不存在

如果默认 activeKey 仍然指向旧模块，例如：

activeKey = 'knowledge'

而新 Tab 只有：

intent / file / experience

页面就可能无法正常切换。

建议默认改为：

activeKey = 'intent'

⸻

可能原因四：点击事件被外层容器遮挡

如果页面上存在透明遮罩、禁用层、loading 层未关闭，也会造成 Tab 无法点击。

检查：

z-index
pointer-events
loading 状态
disabled 状态

2. 删除 AI 修改脚本按钮

原来的：

AI修改脚本

按钮删除。

原因是：当前设计中，AI 生成 SQL、Python 和分析思路发生在后台智能分析引擎中。用户修改脚本后，主要操作应该是保存或执行，而不是在弹窗里再次触发一个边界不清的 AI 修改动作。

⸻

3. 新增三个按钮

脚本弹窗底部保留三个按钮：

按钮	作用
取消	关闭弹窗，不保存修改
保存	保存当前 SQL、Python、分析思路、AI分析总结
执行	使用当前 SQL 和 Python 重新取数并渲染页面

执行逻辑：

用户修改 SQL / Python / 分析思路
→ 点击执行
→ SQL 重新调用 QBI
→ 返回新数据集
→ Python 重新生成可视化
→ 本地小模型重新总结数据结论
→ 页面重新渲染

八、后台智能分析流程

这是整个系统最核心的能力。

后台智能分析引擎不直接体现在页面上，但它决定了智能分析是否真正可用。

1. 输入

智能分析引擎接收两类输入：

用户自然语言问题
或
快捷分析主题

同时还可以接收上下文：

当前机构
当前时间周期
当前用户角色
当前页面
当前选择的数据主题

⸻

2. 第一步：意图识别

系统拿到问题后，先进行意图识别。

优先检索：

知识记忆 → 意图管理

判断用户的问题属于哪个：

分析场景
分析目的

例如：

用户问题：帮我分析财富中收为什么落后？
识别结果：
分析场景：机构经营分析
分析目的：指标落后原因分析
关联主题：财富中收分析
关联指标：财富中收、AUM、理财余额、理财日均净增
关联经验：财富中收分析经验

⸻

3. 如果已有意图匹配成功

系统召回：

主题表
指标字典
原始表字段语义
分析经验
知识文件
历史分析记录

然后进入分析规划。

⸻

4. 如果没有匹配到已有意图

系统不能直接失败，而是进入兜底检索：

指标字典
主题表
知识文件
业务逻辑
原始表字段语义
历史分析经验

基于这些信息形成一个新的候选意图：

新的分析场景
新的分析目的
可能关联的主题
可能使用的指标
可能需要的表

这部分可以作为后续意图管理的候选沉淀。

⸻

5. 第二步：分析规划

分析规划 Agent 根据识别到的意图和召回的知识，拆解分析步骤。

例如：

分析主题：财富中收落后原因分析
步骤一：看整体完成情况
步骤二：看时间趋势变化
步骤三：看机构间差异
步骤四：看客户经理贡献
步骤五：看产品结构
步骤六：看客户结构
步骤七：判断主要原因
步骤八：输出经营建议

每一步都需要明确：

要回答什么问题？
需要哪些指标？
需要哪些表？
需要哪些字段？
SQL 怎么写？
返回什么数据？
适合什么图表？
可能有哪些结论？

⸻

6. 第三步：多 Agent 分工

每一个分析步骤分配给一个 Agent。

例如：

分析步骤	Agent
整体完成情况	经营概览 Agent
趋势变化	趋势分析 Agent
机构差异	机构对比 Agent
客户经理贡献	客户经理分析 Agent
产品结构	产品结构 Agent
客户结构	客户结构 Agent
风险判断	风控 Agent
总结建议	经营总结 Agent

每个 Agent 负责自己的分析片段，但最终由汇总 Agent 整合。

⸻

7. 第四步：GPT-5.5 生成 SQL、Python 和分析思路

根据你的要求，这一步由 GPT-5.5 完成。

GPT-5.5 输出三个核心内容：

第一，分步骤 SQL

每个分析步骤生成一段 SQL。

步骤一 SQL：整体完成情况
步骤二 SQL：趋势变化
步骤三 SQL：机构对比
步骤四 SQL：客户经理贡献
...

第二，分析思路

按步骤输出完整分析路径：

先看整体结果；
再看趋势变化；
再看机构和人员拆分；
再看产品与客户结构；
最后判断主要原因和后续建议。

第三，Python 可视化脚本

根据每个数据集的结构生成图表逻辑，例如：

趋势图
柱状图
排行榜
结构占比图
异常点标记
同比环比对比图

同时，GPT-5.5 还应输出：

可能结论清单
需要验证的方向
可能失效的判断
风险提示

⸻

8. 第五步：SQL 执行与数据集返回

GPT-5.5 生成 SQL 后，系统调用 QBI 的 SQL 执行接口。

流程：

SQL
→ QBI 接口
→ 返回数据集
→ 数据标准化
→ 页面展示

开发阶段可用 Mock 数据。

Mock 数据需要尽量贴近真实返回结构，包括：

字段名
字段类型
时间字段
机构字段
指标字段
金额字段
同比环比字段
排名字段

否则前端渲染和 Python 可视化逻辑容易后期返工。

⸻

9. 第六步：数据展示与可视化渲染

SQL 返回的数据集分两路使用。

第一路：查看数据 Tab

直接展示结构化数据。

分析结果 → 查看数据 Tab

支持：

分页
排序
筛选
导出
字段解释
指标口径查看

⸻

第二路：Python 可视化

系统根据 GPT-5.5 生成的 Python 脚本，对返回数据进行可视化渲染。

数据集
→ Python 脚本
→ 图表结果
→ 可视化分析 Tab

可视化结果展示在：

分析结果 → 可视化分析 Tab

⸻

10. 第七步：本地 4B 小模型生成结论总结

这是你特别补充的关键逻辑。

SQL 把数据取回来之后，系统自动调用本机 4B 小模型，例如：

Qwen3.5-4B

它的职责不是重新写 SQL，也不是重新规划分析路径，而是：

基于已返回的数据集，
结合 GPT-5.5 给出的分析思路和可能结论，
筛选真正被数据支持的结论，
过滤不成立的结论，
最终生成经营分析总结。

也就是说，两个模型分工如下：

模型	职责
GPT-5.5	意图识别、分析规划、SQL 生成、Python 生成、穷举可能结论
Qwen3.5-4B 本地模型	基于真实返回数据筛选结论、总结当前数据真正表达的结果

这能避免一个问题：

GPT-5.5 在没看到真实数据前，只能提出可能结论；真正的结论必须由返回数据验证后再生成。

⸻

九、AI 分析总结设计

AI 分析总结区域应支持编辑。

默认内容由本地 4B 小模型生成，但用户可以人工修改。

建议总结结构如下：

1. 核心结论
2. 主要异常
3. 关键原因
4. 数据证据
5. 经营建议
6. 风险提示
7. 后续跟进动作

例如：

本周财富中收完成率低于目标，主要拖累来自 A 支行和 B 支行。
从客户经理维度看，李强、陈思思贡献低于预期，且存量客户续作率下降明显。
从产品结构看，理财产品销售占比下降，保险类中收未形成有效补充。
建议下周优先跟进高净值存量客户续作，并对低贡献客户经理进行名单制督导。

⸻

十、智能分析结果保存与沉淀

智能分析结果不能只停留在一次性页面展示，而应该能够沉淀为系统资产。

保存后可进入三个方向：

智能分析结果
├── 保存为主题表
├── 保存为分析经验
└── 被经营周报引用

1. 保存为主题表

适合保存稳定可复用的 SQL 和字段结构。

例如：

财富中收分析
客户经理贡献分析
机构经营概览

保存后，可在智能分析页面作为快捷主题展示。

⸻

2. 保存为分析经验

适合保存分析路径和判断逻辑。

例如：

财富中收落后时，优先从机构、客户经理、产品结构、客户结构四个维度拆解。

⸻

3. 被经营周报引用

适合把本次分析结果作为周报模块。

例如：

本周财富中收分析模块
本周客户经理贡献分析模块
本周机构经营概览模块

⸻

十二、关键逻辑修正

原口述中有几个地方需要修正，否则后续开发容易混乱。

1. 数据接入不是页面拉数

原表述容易让人误解为“数据接入页面负责引入数据”。

修正为：

数据接入页面只维护连接配置；
后端服务通过配置调用 QBI 接口；
数据管理页面展示和管理已同步的数据资产。

⸻

2. 原始表和主题表要分清

原始表是底层数据资产。

主题表是分析场景资产。

两者不能混在一起。

原始表：系统知道有哪些底表和字段。
主题表：系统知道哪些分析主题可以复用。

⸻

3. 主题表和分析经验要分清

主题表解决 SQL 和数据结构。

分析经验解决分析逻辑和结论规则。

主题表：取数逻辑。
分析经验：分析逻辑。

⸻

4. GPT-5.5 和本地 4B 小模型职责要分清

GPT-5.5 负责复杂规划和生成。

本地 4B 小模型负责基于真实数据做结论筛选和总结。

GPT-5.5：生成可能性。
Qwen3.5-4B：基于数据确认现实性。

⸻

5. 页面按钮要避免重复

删除：

本轮分析思路按钮
AI修改脚本按钮

统一沉淀到脚本弹窗中。

保留：

取消
保存
执行

这样交互更清晰。

⸻

十三、最终闭环

新版平台的完整闭环是：

系统配置维护模型和数据源
→ QBI 同步原始表和字段元数据
→ 系统补充字段级语义层
→ 主题表沉淀可复用分析 SQL
→ 意图管理维护分析场景和分析目的
→ 分析经验沉淀常规分析路径
→ 用户输入问题或点击快捷主题
→ GPT-5.5 识别意图、拆解步骤、生成 SQL/Python/分析思路
→ QBI 执行 SQL 返回数据
→ Python 渲染可视化
→ 本地 4B 小模型基于真实数据筛选结论
→ 用户编辑、保存、执行
→ 分析结果沉淀为主题表、分析经验或周报模块
→ 经营周报引用分析结果并调整顺序
→ 周报输出后继续沉淀为组织知识

一句话总结：

这次改造的核心，是把智能分析从“用户问一句、大模型答一句”，升级为“基于数据资产、语义层、意图管理、分析经验和多 Agent 分工的可复用分析生产系统”。
